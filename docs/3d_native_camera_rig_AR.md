# كاميرا 3D حقيقية بدون تعديل Kotlin (نظام الـrig)

## المشكلة
مشغّل Filament الحالي (`ModelViewer`) ما يقبل مسار كاميرا حر، فقط أوضاع جاهزة (`orbit`, `push_in`...). وكذلك يُصغّر أي مجسم داخل مكعب وحدة (`transformToUnitCube`). تعديل Kotlin بدون جهاز اختبار خطر يكسر بناء التطبيق، لذلك لم نلمسه.

## الحل
الـGLB يحمل **أنيميشن واحد على عقدة أب `world_rig`** تحرّك العالم كله بعكس حركة الكاميرا. الكاميرا الأصلية ثابتة، فترى بالضبط ما كانت ستراه كاميرا حقيقية متحركة. المشغّل يشغّل أنيميشن glTF أصلاً (`updateModelAnimation`).

```
R(P) = eye + Rot * (P - p)      // Rot = صفوف (right, up, back) للكاميرا الافتراضية
eye = center + (0, 0, 5 / scale) // عين الكاميرا الأصلية بوحدات العالم
native = (world - center) * scale + (0, 0, -4)   // transformToUnitCube
```
الفرق بين فضاء الكاميرتين تكبير منتظم فقط، والإسقاط المنظوري لا يتأثر به.

## الملفات
- `lib/world3d_rig.dart`: ثوابت كاميرا المشغّل، `World3DBounds`، رياضيات quaternion، `World3DRig.rigFor` و`World3DRig.build`.
- `lib/world3d_glb_builder.dart`: `build(scene, cameraSeconds: 3)` يكتب الـrig والأنيميشن. المواقع صارت مخبوزة داخل الـvertices (لا translation على العقد)، فلا يعتمد حساب المكعب على transforms العقد.
- استخدم `World3DNativeCamera.stage()` لتخطيط المشهد: زاوية العدسة تطابق المشغّل فيظهر التخطيط مثل 2D عند ثبات الكاميرا.

## افتراضات يجب تأكيدها على جهاز حقيقي (لم أستطع تشغيلها هنا)
1. زاوية الرؤية العمودية للمشغّل = 2·atan(12/28) ≈ 46.4° (عدسة 28 مم على حساس ارتفاعه 24 مم). لو اختلفت فعدّل `World3DNativeCamera.focalLengthMm` / `sensorHeightMm` فقط.
2. `transformToUnitCube` يضع مركز المجسم على (0,0,-4) ويجعل أطول ضلع = 2.
3. قبل التصوير يجب استدعاء `setCameraMotion(mode: 'manual')` حتى تبقى الكاميرا الأصلية ثابتة، ثم `captureFrames` (مدة التصوير = مدة الحركة من الـGLB بدون الثباتات). الأنيميشن يبدأ بثبات نصف ثانية وينتهي بثبات نصف ثانية لتغطية بداية اللقطات.

## حدود معروفة
- الـdolly zoom يبقى بحركة الكاميرا فقط (زاوية العدسة ثابتة في المشغّل).
- الـrig يتطلب نسبة عرض/ارتفاع الـView الأصلية مثل `stage.aspect` (9:16 افتراضياً).

## الدفعة القادمة
ربط `ThreeDScenePipeline` بالموجّه: خطة مشهد (تخطيط ← GLB ← فحص ← تحميل ← manual ← تصوير) مع fallback لـ 2.5D عند أي فشل.
